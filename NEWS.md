- Added runs-of-homozygosity (ROH) detection and per-sample FROH, the other genuine gap flagged alongside kinship earlier this session: diversity's `inbreeding_coefficient` is a population-level FIS summary and kinship is pairwise, but neither captures the per-sample, per-genomic-region signal of long homozygous stretches (a standard inbreeding/autozygosity indicator). Uses `bcftools roh` (Narasimhan et al. 2016, HMM-based, the modern standard method) -- `bcftools` is already a **required** `SystemRequirements` dependency (used for VCF sorting/BGZF/indexing before the pipeline can even build a GDS), so this adds **no new dependency at all**. The only CRAN alternative, `detectRUNS`, was checked and rejected: last updated 2019, `NeedsCompilation: yes`, and pulls in 6 dated transitive dependencies (`plyr`/`iterators`/`itertools`/`reshape2`/`Rcpp`/`gridExtra`) for one feature. Verified empirically against real data before committing to the design: `bcftools roh -G30 --estimate-AF -` (self-estimated allele frequencies from the analyzed samples -- this package has no mechanism to attach an external reference-panel AF to an arbitrary VCF, so self-estimation is the only sound default) against the real, already-approved chr22 1000 Genomes region gave real, plausible signal (a 15-sample real multi-population subset: 1-4 runs of 15-160kb per sample within a 1Mb window, FROH 0.02-0.4); confirmed `--AF-dflt` (a naive constant AF) produces obviously-degenerate output (near-100%-of-window "runs" for every sample), ruling it out. Deliberately does **not** apply this package's fixed MAF filter (`maf=0.05`) before ROH calling -- MAF filtering is appropriate for PCA/structure work but is known in the ROH literature (Purcell et al. 2007; McQuillan et al. 2008) to bias run lengths downward by removing informative rare-homozygous tracts; ROH instead reuses only the *missingness* half of the fixed QC contract (`F_MISSING > 0.2`, i.e. `cfg$qc$max_variant_missing`, not a new config key) plus a biallelic-SNP-only restriction. New `R/roh.R`: `run_roh()` derives the exact analyzed sample/site subset via one `bcftools view` call, computes the **analyzed genomic footprint** (not the whole genome -- this package accepts arbitrary VCF inputs, so a single-region VCF and a whole-genome VCF give very different FROH for the same biology) from that same site set, and calls `bcftools roh`, producing a full per-run table and a per-sample summary where a sample with zero detected runs still appears with `n_runs=0`/`froh=0` (real information, not silently omitted). New module `roh_module_spec()` writes `37_ROH_runs.tsv`, `38_ROH_sample_summary.tsv`, and two new figures: `23_ROH_length_distribution` (log-scale histogram, skipped only when zero runs exist anywhere) and `24_ROH_FROH_by_sample` (always drawn, coloured by population when available). New `analyses.roh` config key (default `TRUE`, like `ibs`/`kinship` -- bcftools being mandatory rather than optional is exactly why) and `analyses.roh_gt_error_phred` (default 30, bcftools's own documented "safe value... to account for GT errors"). Deliberately does not impose any short/medium/long ROH-length classification convention (species/study-specific, not a property of the estimator itself, unlike KING's kinship thresholds) and does not expose genetic-map/HMM-transition-probability tuning (no supply mechanism for species-specific genetic maps in this general-purpose tool). Report gained a NULL-safe "Runs of homozygosity" section (highest-FROH samples, capped at 20, pointing to the complete on-disk table), matching the "Close relatives"/"Private alleles" precedent. Verified with a new `test-roh.R`, including a purpose-built synthetic VCF fixture with real, verifiable ground truth (one sample homozygous throughout -> one run spanning the full analyzed span; one heterozygous throughout -> zero runs), plus real-data smoke checks against the cached chr22 region and the tiny bundled CI fixture (structural-only, matching the established HWE/kinship precedent for that undersized fixture). No public API changes: only `roh_module_spec()` is exported, matching every other `*_module_spec()`.
- Added pairwise sample kinship/relatedness estimation, a genuine gap distinct from the existing IBS analysis: IBS answers "how similar are these samples overall," kinship answers "are these two individuals related, and how closely" -- the standard upstream check for cryptic relatives, which silently biases FST, diversity, and structure analyses computed downstream. Uses `SNPRelate::snpgdsIBDKING()` (KING-robust, Manichaikul et al. 2010, already an SNPRelate dependency -- no new package). `type = "KING-robust"` is hardcoded rather than exposed as a config toggle: `"KING-homo"` assumes a single homogeneous population and would silently give biased results whenever real population structure exists, which this package explicitly supports. Verified empirically before committing to the design: the tiny 9-SNP CI validation fixture gave nonsensical kinship values (outside the theoretical bounds, including identical values for a same-population pair and an arbitrary pair), confirming KING genuinely needs realistic marker density; the real, already-approved chr22 1000 Genomes region (2,504 samples x 21,418 SNPs) gave real signal (the two highest-kinship pairs ~0.48, consistent with 1000 Genomes Phase 3's known duplicate/MZ-twin pairs) in 6.5 seconds. Also discovered empirically, and important for interpretation: KING-robust's kinship estimator is bounded above at 0.5 (self/duplicate) but is **not** bounded below at -0.5 for arbitrarily divergent pairs -- real chr22 data restricted to the pipeline's own LD-pruned SNP set showed off-diagonal kinship as low as -8 for pairs spanning highly differentiated continental populations, so the new validator only enforces the upper bound. New `R/kinship.R`: `run_kinship()` (mirrors `run_ibs()`'s exact filtering defaults) returns the kinship matrix, IBS0 matrix, and a long-form pairs table joined to each member's population, classified into `relationship_degree` (`"duplicate/MZ twin"`, `"1st-degree"`, `"2nd-degree"`, `"3rd-degree"`, `"unrelated"`) using the standard KING thresholds (Manichaikul et al. 2010, not invented). `plot_kinship()` draws `21_kinship_heatmap` (gated at <=300 samples, matching `plot_ibs()`'s existing gate; clusters on a kinship-derived pseudo-distance via the already-generic `hclust_dendrogram_segments()` helper, but displays the real kinship coefficient as fill) and `22_kinship_IBS0_vs_kinship` (the standard KING diagnostic scatter, coloured by relationship degree). New module `kinship_module_spec()` writes `33_kinship_matrix.tsv`, `34_kinship_IBS0_matrix.tsv`, `35_kinship_pairs.tsv` (every pair), and a filtered `36_close_relatives.tsv` (only pairs above the new `analyses.kinship_close_relative_threshold` config key, default 0.0442, the 3rd-degree cutoff -- configurable since which degree counts as "close enough to flag" is a legitimate per-study policy choice, unlike the classification scale itself). New `analyses.kinship` config key (default `TRUE`, like `ibs` -- needs only genotypes, no population/geographic metadata required). Report gained a NULL-safe "Close relatives" section (capped at 20 rows, pointing to the complete on-disk table), matching the "Private alleles" section's precedent; the full O(n^2) matrices are intentionally not surfaced in the report, matching how IBS's own matrices aren't either. Verified with a new `test-kinship.R` (relationship-degree classification at every threshold boundary; `run_kinship()` against a synthetic fixture with a known exact duplicate and a simulated Mendelian parent-offspring pair, both real ground truth, not the undersized 9-SNP fixture; module-spec and validator coverage), extended `test-config.R` and `test-pipeline.R` coverage. - Added per-population Hardy-Weinberg equilibrium (HWE) testing and private-allele detection to the `diversity` analysis, reusing per-locus-per-population data (`x`, `p`, `n_called`) `compute_diversity()` already computed rather than adding a parallel computation.
