- **Reported directly against the same real production report: the DAPC PC-count cross-validation figure (`12b_DAPC_xval_K<k>`) was missing entirely, every K showed exactly the same "40 PCA axes retained" (suspiciously round for a supposedly cross-validated choice), and the K=3 scatter showed nearly every sample collapsed onto one point -- the classic DAPC over-fitting signature.** All three were the same root cause. `adegenet::xvalDapc()` -- unlike `adegenet::glPca()`, used everywhere else in `run_dapc_k_task()` (`R/dapc.R`) -- calls `ade4::dudi.pca()` directly on whatever data it's given, which hard-errors on any missing genotype (`"na entries in table"`); a real QC-passing marker set legitimately contains missing calls (QC bounds missingness, it doesn't eliminate it), so cross-validation was failing on *every* K, always caught by a bare `tryCatch(..., error = function(e) NULL)` with no log line at all, silently falling back to a crude `floor(0.8 * n_samples)` PC count instead -- confirmed directly by reproducing the exact error against the real cached GDS. - **Requested: a seventh gap-audit pass, on three classic base-R pitfall patterns not yet specifically targeted -- `1:n`-style off-by-one bugs on zero-length input, `sapply()`/vectorized-`if` type instability, and algorithmic scalability at real production scale.** The `1:n` audit came back genuinely clean (this codebase consistently uses `seq_len()`/`seq_along()` throughout -- only two colon-range constructs exist anywhere in `R/`, both already safely guarded) and `sapply()` is never used at all (this codebase exclusively uses `vapply()`). The other two found real, live issues.

  1. **`validate_config()` (`R/config.R`) -- the very first code every real pipeline run executes -- either crashed with a cryptic, generic R error or, for at least two fields, silently accepted a malformed config value with no error at all.** Every scalar-valued config leaf's own range/finiteness check (`if (!is.finite(x) || x > bound)`-style, dozens of them) assumes `x` already has length 1. A malformed config -- a realistic mistake, e.g. an accidental YAML sequence like `maf: [0.1, 0.6]` from a copy-paste or formatting slip -- reaches these checks as a multi-element vector instead: `if()` on a length > 1 condition is a hard error on every R version this package supports (`DESCRIPTION` requires R >= 4.3), so most fields crashed with `"the condition has length > 1"` instead of this codebase's otherwise-consistent clear diagnostics. Worse, two fields (`max_sample_missing`, `ld_r2`) are checked only via a vectorized `any()` over a combined value vector -- both individually in-range elements passed that check silently, and neither field was ever coerced back to scalar afterward, so `validate_config()` returned a genuinely malformed length-2 config with **no error raised at all**. Fixed with a single, comprehensive scalar-length guard added early in `validate_config()`, checking every one of the ~48 scalar-expected config leaves up front and reporting every offending one by name in one clear, uniform error -- before any individual comparison can crash or silently mismeasure a multi-element value. New tests cover both the crash case (`maf`) and both silent-pass cases (`max_sample_missing`, `ld_r2`), plus a sex-check threshold, `sexbias_test`, and the genuinely-optional `pcadapt_k`.

  2. **`run_genome_scan_fst()`/`run_genome_scan_diversity()` (`R/genome_scan.R`) re-scanned the *entire* retained marker set (or, for diversity, the entire population-wide locus set) for every single genome-scan window, instead of restricting the scan to that window's own chromosome first.** At the config defaults (50kb window/step) against this session's own real production example (561,767 loci), that's roughly 20,000 windows each doing an O(n_loci) linear scan -- true O(n_windows × n_loci) instead of the O(n_windows × n_loci_per_chromosome) the already-per-chromosome window construction (`genome_scan_windows()`) makes straightforward to achieve, with the diversity side further repeating the same redundant work once per population. Fixed by pre-splitting the marker/locus positions by chromosome once, so each window's scan is restricted to its own chromosome's subset -- a pure search-space restriction with no semantic change (the same final SNP/locus selection either way), verified by the existing exact-match serial-vs-parallel tests continuing to pass unchanged at real scale (98,922 variants, 160 samples).

- **Requested: a sixth gap-audit pass, on three fresh angles -- locale/sort-order reproducibility, numerical stability under real floating-point edge cases (a different lens than the formula-correctness checks already done), and cross-platform Windows path/fork-guard consistency.** All three found real, live bugs.

  1. **Locale-dependent `sort()` could silently change figure colours/shapes and table row order depending on which machine ran the analysis.** `population_palette()`/`population_shapes()` (`R/utils.R`) sorted population names with base R's default, locale-sensitive collation -- empirically confirmed on this platform: the same mixed-case population set sorts differently under a `"C"` locale than under `"en_US.UTF-8"`, silently assigning different colours/shapes to the same populations across figures (PCA, DAPC, trees, ...) depending on the runtime locale, with no indication anything differed. `compute_jost_d()` (`R/jost_d.R`) and `run_bottleneck_analysis()` (`R/bottleneck.R`) had the same issue affecting written table row order. `natural_sort_levels()` (`R/utils.R`, used for Manhattan-plot chromosome ordering) had a related gap: its digit-padding only protects purely-numeric comparisons, not the underlying character ordering for non-digit runs (`"X"`/`"Y"`/`"MT"`-style names). All four fixed by sorting with `method = "radix"`, which R documents as platform-independent for character vectors (verified directly: identical output under both locales tested) -- giving this package's figures and tables the same cross-machine reproducibility guarantee its checkpoint/config fingerprints already have. New test asserts `population_palette()`/`population_shapes()` output matches the fixed radix order directly, without needing to actually switch locales in CI.

  2. **`spatial_autocorrelation_r()` (`R/spatial_autocorrelation.R`) crashed with "missing value where TRUE/FALSE needed" on real, non-adversarial input: a sample pair sharing zero non-missing genotyped loci after QC.** `stats::dist()` returns `NA` for such a pair; `rs`/`sgd` already used `na.rm = TRUE` (showing this was anticipated), but the per-bin `cx`/`cxii`/`cxjj` sums downstream did not, so a single `NA` pair propagated into `denom`, and `if (denom == 0)` on an `NA` denominator is a hard R error, not the graceful `NA_real_` this function clearly intends for the analogous zero-denominator case. Fixed with `na.rm = TRUE` on all three sums and an explicit `is.na(denom)` guard.

  3. **`haversine_matrix()` (`R/mantel_ibd.R`, shared by `run_mantel_ibd()` and `run_spatial_autocorrelation()`) could return `NaN` for real geographic coordinates.** Its intermediate `a` term is mathematically bounded in `[0, 1]` but is a sum of two independently-rounded trig terms; for near-antipodal coordinates, floating-point rounding pushes it fractionally above 1, and the unclamped `sqrt(1 - a)` silently returns `NaN` (a well-known haversine-formula pitfall). Confirmed directly with an exact antipodal coordinate pair (lat -89.26/89.26, lon -180/0) that triggers `a > 1` on this platform. Fixed by clamping `a` to `[0, 1]` before both `sqrt()` calls; new test verifies the same pair now returns the correct antipodal distance (~20015 km) instead of `NaN`.

  4. **`run_tree_bootstrap_replicates()` (`R/tree_bootstrap.R`) -- reached via `build_nj_tree()`/`build_population_tree()` -- was the only remaining `mclapply()` path in the codebase that didn't route its worker count through `fork_worker_count()`, the shared Windows/task-count/thread-budget guard every other fork site uses.** Both real callers passed `cfg$compute$threads` straight through as `workers`. Not an active crash -- `mclapply()` itself already forces `mc.cores = 1` on Windows -- but a real, live inconsistency that also meant this path skipped `fork_worker_count()`'s other protections (NA/zero/negative-threads coercion). Fixed by re-deriving `workers` via `fork_worker_count()` inside the shared helper itself, closing the gap for every current and future caller at its root; new test proves an `NA` `workers` value (which would have hit `if (NA)` and crashed under the old code, the same error class fixed in finding 2 above) is now handled cleanly.

  Everything else checked -- the numerical-stability audit's broader sweep of Fst/diversity/AMOVA/kinship/DAPC-diagnostics/Ne-LD/genome-scan formulas for NaN/Inf propagation and degenerate-input handling, and the Windows audit's check of hardcoded path separators, `/tmp` literals, and executable resolution -- came back clean (a minor, non-live `file.access()` platform-semantics note in `R/vcf_input.R` was judged not worth prioritizing: it only gates a pure optimization, not a correctness path). Full local test suite re-run clean: 4566 passed, 0 failed.

  1. **Security: `--resume`'s checkpoint-loading path (`read_execution_checkpoint()`, `R/execution-checkpoint.R`) documented its SHA-256 sidecar in a way that overstated the protection it actually provides.** The sidecar is written next to the checkpoint by the same ordinary write, so it detects accidental corruption (a truncated copy, a partial write) but provides no defense against a deliberate attacker, who can just as easily recompute and replace a matching sidecar for a crafted payload -- and `readRDS()`, which this function ultimately calls, can execute arbitrary R code embedded in a maliciously crafted file the moment it is deserialized, a documented, general property of R's own serialization format. This is inherent to using RDS for checkpoints at all, not a code defect fixable without a larger architecture change (cryptographic signing, or a sandboxed loader) that wasn't undertaken unilaterally here -- instead, `write_execution_checkpoint()`'s/`read_execution_checkpoint()`'s own docstrings, `man/execution_checkpoint.Rd`, and `wiki/Deployment-and-Troubleshooting.md`'s `--resume` section were all corrected to state the real trust boundary plainly: only ever resume from an `output.directory` your own runs produced, never one downloaded, received from a collaborator, or restored from storage you don't fully control.

(2) `run_genome_scan_fst()`'s per-window loop: a genome-wide scan has thousands of windows, each individually *cheap* (one `snpgdsFst()` call over a handful of SNPs) -- forking one process per window the way `fst`/`diversity` fork per task would pay fork overhead thousands of times over for little work each, so windows are instead split into exactly `workers` contiguous chunks via `parallel::splitIndices()` (the same balanced-partitioning helper `mclapply()` uses internally), and each worker opens one GDS connection and processes its whole chunk. (3) `run_genome_scan_diversity()`'s per-population loop: pure R/`data.table` work computed from the already-materialized locus table, no GDS handle involved at all, so it forks directly per population with no per-worker-connection dance -- the same profile as `diversity`'s own parallelization, just without the extra safety machinery that turns out not to be needed here. `bootstrap_fst()` was deliberately left sequential, out of scope: it is optional, gated behind `cfg$analyses$bootstrap$enabled`. Verified with new unit tests (`test-fst-parallel.R`, `test-genome-scan-parallel.R`: parallel output matches serial to `1e-12`, sequential fallback confirmed when no `gds_path` is supplied, and a forced per-worker/per-chunk failure surfaces a clear error rather than a corrupted result) and a real end-to-end pipeline run on the 160-sample, 8-population, ~99K-SNP quickstart dataset confirming identical `fst`/`genome_scan` output between `threads = 1` and `threads = 3`.

- **Vectorized `population_tree`'s per-SNP allele-count matrix assembly, replacing an R-level `for` loop with two whole-matrix column assignments.** Found alongside the `diversity` parallelization above while surveying which modules could benefit from performance work on the same real production cohort: `population_allele_count_matrix()` builds the interleaved reference/alternate allele-count matrix that `adegenet::genpop()`/`dist.genpop()` consume for Nei's distance, from the full `diversity_full$locus` table (the same 500K+ QC-passing-locus scale as the `diversity` module itself, not the LD-pruned subset) -- but did so with a `for` loop assigning two columns per SNP one iteration at a time, an R-level cost that grows with locus count on every real run since `population_tree` is enabled by default. Replaced with two vectorized assignments (`tab[, ref_cols] <- as.matrix(ref_wide[, snp_ids, with = FALSE])`, same for `alt_cols`) that do the identical interleave via whole-matrix column indexing; both wide tables are still indexed by the same `snp_ids` name vector rather than assumed column order, so this stays correct even if `dcast()` ever ordered the two tables differently. Verified: byte-identical output against the original loop at 50,000 loci (1.16s vectorized vs. 18.7s looped, ~16x), and the existing `test-population-tree.R` (26 assertions, including the Nei's-D hand-calculation and monotonic-divergence checks) and `test-tree-bootstrap.R` suites both pass unchanged.

- **Parallelized the `diversity` module's per-population locus statistics (`lapply` -> `mclapply`) after a real production run took 57 minutes on a 561,767-locus unpruned cohort.** Investigated after the same real user asked whether the long-running `clonality` module (separately confirmed genuinely slow rather than hung, via live `ps`/`stat` inspection of their production log) could be sped up with parallelism, and whether other modules could benefit similarly; `diversity` was the clearest win, since its per-population HWE/allele-frequency/private-allele computation is already an embarrassingly-parallel `lapply` over populations. Forking while sharing the parent's already-open GDS handle is genuinely unsafe -- `gdsfmt`'s own documentation (`tools::Rd_db("gdsfmt")[["openfn.gds.Rd"]]`) states forked children inherit the parent's shared file descriptor/offset, causing "wrong reading, even program crashes" under concurrent access -- so each forked worker now opens its own independent, read-only GDS connection (`SNPRelate::snpgdsOpen(gds_path, allow.duplicate = TRUE, allow.fork = TRUE)`) rather than reusing the shared handle; `compute_diversity()` falls back to the original sequential path whenever no `gds_path` is available (e.g. the small CI fixture in `scientific_validation.R`), so behavior there is unchanged. Generalized DAPC's existing `dapc_worker_count()` fork-sizing helper into a shared `fork_worker_count()` in `R/utils.R` (bounds worker count by task count, thread budget, and platform fork support) rather than duplicating the same bounding logic a second time. Failed workers surface as a clear `stop()` naming the failed population(s) instead of a silently corrupted result. Verified with new unit tests (`test-fork-worker-count.R`, `test-diversity-parallel.R`: parallel output identical to serial to `1e-12`, sequential fallback confirmed when no `gds_path` is supplied, and a forced per-worker failure surfaces the expected error) and a real end-to-end pipeline run confirming byte-identical `diversity` output between `threads = 1` and `threads = 3`. `population_assignment`'s separate, already-fast (~10s) `compute_diversity()` call is deliberately left sequential-only, out of scope for this change.

- Added Nei's (1987) Dxy, absolute nucleotide divergence between populations, to the `fst` module. Found by a second standard-toolkit gap audit (SambaR's `calcdistance()` and PopGenome both list Dxy alongside FST as a core differentiation statistic). Genuinely distinct from every FST-family measure already computed here (global/pairwise FST, Wright's Nm, Jost's D, Weir and Goudet's population-specific beta): all four are normalized by within-population diversity, while Dxy is not, so a pair can show identically low FST with either low Dxy (recent divergence, ongoing gene flow) or high Dxy (an older split still sharing substantial ancestral polymorphism) -- two different demographic histories FST alone cannot distinguish (Cruickshank and Hahn 2014). New `R/dxy.R`: per-locus `p1*(1-p2) + p2*(1-p1)` (the probability a randomly drawn allele from each population differs), averaged across loci where both populations have at least one called genotype -- the same "usable loci" convention `compute_jost_d()`/the population tree's Nei's-distance already use, and no finite-sample bias correction, matching how Dxy is defined and reported in the literature (unlike Jost's D's bias-corrected Hs/Ht). Unlike FST and Jost's D, Dxy has no natural multi-population generalization (it is fundamentally a divergence between two specific gene pools), so the reported `global_dxy` is explicitly documented as the mean of the pairwise matrix, not a separate multi-population estimator -- a deliberately weaker, honestly-scoped claim than the other three "global" values in the same table.   **`admit_execution_resources()` was stateless.** Each call checked one module's requirements against a resource policy's fixed capacity in isolation, with no shared record of what else was already admitted and still running against that same policy -- so two genuinely concurrent, overlapping admissions each saw the *full* capacity independently, providing no real protection against joint oversubscription once more than one was actually in flight at once. Not reachable anywhere in this package's own pipeline today (ADMIXTURE and fastStructure both run one external process at a time, never concurrently), but a real gap in the public contract of the exported async supervision API (`start_supervised_external_command()` and friends), which document themselves as "deterministic concurrent scheduling." Fixed with an explicit `in_use` parameter on `admit_execution_resources()` (default all-zero, exactly reproducing prior behavior for every existing caller) and a session-scoped ledger (`admission_ledger_in_use()`/`_commit()`/`_release()`) that `start_supervised_external_command()` now consults and updates, releasing on `set_async_terminal()` -- with a `reg.finalizer()` safety net that releases a handle's commitment if it is garbage-collected without ever being finalized, rather than leaking it for the rest of the R session. Honestly scoped: this ledger is per-R-session state and cannot, and does not attempt to, coordinate admission across separate forked/parallel worker processes (e.g. `parallel::mclapply()`), since each fork gets its own independent copy of R's memory. Verified with new tests: `admit_execution_resources()`'s `in_use` reduces available capacity as expected; two overlapping async handles under a `processes = 1` policy now genuinely compete (the second is rejected while the first is still running, then admitted once the first finalizes); and the GC-based safety net actually releases an abandoned handle's commitment.

  **The VCF-normalization cache trusted mtime, not content.** `prepare_vcf_input()` treated its cached, sorted/BGZF-compressed/indexed copy as current whenever its mtime was `>=` the source VCF's mtime, without ever checking content -- a source VCF replaced with different content but an equal-or-older mtime (e.g. restored from a backup or via `git checkout`, both of which can leave an older or unchanged mtime on genuinely new content) would silently serve stale cached genotypes for the rest of the run, with no error or warning. Fixed by keying cache validity on a `digest::digest(vcf, algo = "sha256", file = TRUE)` content fingerprint recorded in a small sidecar file next to the cache, checked on every call instead of comparing timestamps; hashing costs far less than the sort/index step this cache exists to avoid, so there is no fast-path short-circuit that could reintroduce the same class of bug. Verified with new tests: an unchanged source correctly reuses the cache (cached file's mtime is untouched by a second call); a source whose content changed but whose mtime was deliberately set *older* than the existing cache (the exact scenario that defeated the old check) is correctly detected as stale and rebuilt; and `force = TRUE` still always rebuilds.

  **Release-candidate evidence artifacts could alias the same underlying content under two different declared paths.** `evaluate_release_candidate_dossier()` already rejected duplicate *declared path strings*, but a symlink, hard link, or a literal duplicate copy could make two different declared paths resolve to byte-identical content, letting one physical file be checksummed and counted as two independent pieces of retained evidence. - Added LD-based contemporary effective population size (Ne), the next gap found by the same standard-toolkit audit that surfaced kinship, ROH, genome scans, LD decay, and allelic richness -- and a natural extension of the LD-decay module added just above, though it needs an unrelated pair-selection strategy (unlinked pairs, not physically close ones).

  New `ne_ld` module (`R/ne_ld.R`, on by default via `analyses.ne_ld`, per population like `diversity`) implements the Waples (2006)/Waples & Do (2008) "LDNe" method: per-population Ne from mean r-squared between *cross-chromosome* SNP pairs (`SNPRelate::snpgdsLDMat(..., slide = -1)`, the already-verified full-pairwise-matrix mode, restricted to pairs on different chromosomes -- the opposite pair selection from `ld_decay`, which specifically wants physically close pairs), bias-corrected for sampling noise, then converted to Ne via `Ne = (1/3 + sqrt(1/9 - 2.76*r2_drift)) / (2*r2_drift)`. Reuses this package's existing QC MAF filter (default 0.05) to satisfy the bias correction's own documented rare-allele-exclusion assumption, rather than adding a redundant `Pcrit` parameter. r-squared attributable to drift at or below the sampling-noise floor is reported as `Ne = Inf` (no detectable signal, not a fabricated finite number, matching NeEstimator's own convention); an implied-Ne below the formula's valid domain is reported as `NA` with an explicit `below_formula_domain` status, never a bogus complex/negative root.

Root cause: KING-robust kinship's denominator depends on each sample's own heterozygosity count, and a hemizygous male has zero heterozygosity on X by construction, so any pair involving a male sample is mathematically degenerate on chromosome-X-only markers -- pooling those markers into the same estimate as autosomal ones dilutes/corrupts the result.
