# popgenVCF 0.10.0

- Added per-population Hardy-Weinberg equilibrium (HWE) testing and private-allele detection to the `diversity` analysis, reusing per-locus-per-population data (`x`, `p`, `n_called`) `compute_diversity()` already computed rather than adding a parallel computation. HWE uses `SNPRelate::snpgdsHWE()` (the exact Wigginton et al. 2005 test, already a dependency, confirmed to return one p-value per requested SNP in request order) called once per population; loci monomorphic *within that population* are reported as `NA` rather than SNPRelate's trivial `p = 1`, since piling spurious `p = 1` values into the summary counts and histogram would misrepresent "not tested" as "not rejected". Private alleles use the standard presence/absence definition (matches hierfstat's/poppr's `private.alleles()`): an allele is private to a population when every copy of it, genome-wide across all retained populations, is found in that one population; the `private_allele` column can be `"ref"`, `"alt"`, `"both"` (the rare case where every *other* population has zero calls at that locus), or `"none"`, and correctly excludes cases where a population merely appears monomorphic locally but another population's heterozygotes still carry the "missing" allele -- verified with a hand-constructed synthetic GDS (built via `SNPRelate::snpgdsCreateGeno()`) covering all four outcomes plus the fewer-than-two-populations no-op case. This is reporting-only: no new QC gate, no SNP filtering. New outputs: `09_population_diversity.tsv` gains `hwe_tested_loci`/`hwe_significant_loci`/`hwe_significant_loci_fdr` (Benjamini-Hochberg via `stats::p.adjust`)/`private_allele_loci`; `10_population_locus_diversity.tsv` gains `hwe_pvalue`/`reference_allele_count`/`private_allele`; a new filtered `32_private_alleles.tsv` lists just the loci with a private allele; two new figures, `19_HWE_pvalues` (p-value histogram faceted by population, styled like `01_MAF`'s threshold-line histogram) and `20_private_alleles` (bar chart by population), both skipped when there is nothing to show. New `analyses.hwe_alpha` config key (default 0.05). Verified with a new `test-diversity-hwe-private-alleles.R`, extended `test-config.R` and `test-pipeline.R` coverage, and visual inspection of the rendered PNGs against real data.
- Added a PCA SNP-loading Manhattan plot and a rank-ordered loading plot, plus a companion top-contributing-SNP table, mirroring the DAPC loading feature below but adapted to PCA's real differences rather than blindly copying the DAPC schema. Loadings come from `SNPRelate::snpgdsPCASNPLoading()`, computed once from the already-fitted PCA object (no new model fitting) only on the primary SNPRelate eigensystem path -- the rare covariance-eigendecomposition fallback path (used when SNPRelate's own eigensystem is non-finite) cannot be fed through `snpgdsPCASNPLoading()` meaningfully, so loadings are honestly `NULL` there rather than computed from a substituted eigendecomposition. Unlike DAPC's `var.contr` (always non-negative), PCA SNP loadings are signed correlations between each SNP and each component, so the new `pca_loading_table()` keeps the signed `contribution` for both plots (showing direction) alongside a `magnitude` column used only for top-N ranking and sort order -- "top contributing" means largest `|loading|`, not largest raw value. The join to chromosome/position is by real SNP ID via `match()` against `snpgdsPCASNPLoading()`'s own returned `snp.id` (which can be a strict subset of the requested SNPs, e.g. via `remove.monosnp`), not by position -- confirmed empirically against the real validation fixture, where one of nine SNPs was dropped this way. `run_pca()` gained an optional `ids` parameter (the same `get_gds_ids()`-shaped lookup already threaded everywhere else in the pipeline); loadings are remapped from raw SNPRelate component indices to the pipeline's final retained `PC1..PCn` numbering, since some requested components can be dropped for non-positive variance. `plot_pca()` draws `17_PCA_loadings_manhattan` and `18_PCA_loadings_ranked` (reusing the DAPC feature's `manhattan_layout()` helper) when loadings are present; `run_module_pca()` writes the top-N-per-axis table as `31_PCA_loadings.tsv`, where N is the new `analyses.pca_loading_top_n` config key (default 20). Verified with a new `test-pca-loadings.R` (the `snploading` join/rank/magnitude logic, the real-fixture end-to-end path, and the `ids`-supplied vs. omitted paths), extended `test-config.R` and `test-pipeline.R` coverage, and visual inspection of the rendered PNGs against real data.
- Added a DAPC SNP-loading Manhattan plot and a rank-ordered loading plot, plus a companion top-contributing-SNP table, for every configured DAPC K value. `adegenet::dapc()` already computes `var.contr` (per-SNP contribution to each discriminant function) as part of fitting each K, so this adds no new model fitting -- only cheap post-processing of results that were already being produced. `genlight_from_gds()` now accepts an optional `snp_ids` argument to set `locNames()` on the genlight object; the new `dapc_loading_table()` reads `model$var.contr` and joins it to chromosome/position by *position*, not by row name -- `var.contr`'s rownames turned out to be plain positional indices ("1", "2", ...), not the genlight object's locus names, discovered by inspecting a real fitted model rather than assuming adegenet propagates names through. `run_dapc_analysis()`/`run_dapc_k_task()` gained optional `snp_ids`/`chromosome`/`position` parameters (default `NULL`, so the unrelated unsupervised-clustering caller in `population_structure.R` is unaffected) and store the resulting long-form loading table per K. `plot_dapc()` draws both new figures per K from that table when present: `15_DAPC_loadings_manhattan_K<k>` (x = genomic position via a new `manhattan_layout()` helper in `R/utils.R`, alternating chromosome colours, faceted by discriminant function) and `16_DAPC_loadings_ranked_K<k>` (x = SNP rank by descending contribution, adegenet's classic `loadingplot()` style). `run_module_dapc()` writes the top-N-per-axis table as `22f_DAPC_loadings_K<k>.tsv`, where N is the new `analyses.dapc_loading_top_n` config key (default 20). Scoped to every configured K (not just the best K): the expensive DAPC fitting already happens for every K regardless, so restricting to the best K would only reduce output file count, not save meaningful compute. Verified with a new `test-dapc-loadings.R` (layout offsets, the `var.contr` join/sort, and the `snp_ids`-supplied vs. omitted paths), extended `test-dapc-plots.R` and `test-config.R` coverage, and a real end-to-end `run_pipeline()` run against the validation fixture with visual inspection of the rendered PNGs.
