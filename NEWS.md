# popgenVCF 0.10.0

- Ordered the population-organized ancestry membership figures (ADMIXTURE, fastStructure, sNMF, and DAPC) by ancestry-pattern similarity instead of alphabetically, following user feedback that alphabetical population order scatters genetically similar populations arbitrarily far apart in the plot (e.g. two African populations could land at opposite ends of the panel purely because their names start with different letters). `plot_q_matrix()` (`R/admixture.R`) is the single shared function all four callers already route through (`R/nonhuman_plink_export.R`'s ADMIXTURE/fastStructure runners, `R/module_registry.R`'s sNMF runner, and `R/dapc.R`'s membership plot), so the fix lives in one place, not duplicated per backend. New `population_ancestry_similarity_order()` helper: average-linkage hierarchical clustering (the same linkage convention this package's kinship dendrogram already uses) on Euclidean distance between each population's mean per-cluster ancestry proportions, computed fresh per K (a population's ancestry profile differs across K). Only the population-organized view's row and facet order changes; the data-driven view (already ordered by dominant-cluster membership, not population identity) and the raw `.tsv` output tables (which record samples in their original file order, unaffected by this purely visual reordering) are untouched. Real quickstart result at ADMIXTURE K=7: LWK and YRI (both African), ITU and STU (both South Asian), and GBR and PUR (both dominated by the same admixed-ancestry component) are now each adjacent pairs instead of being separated by 1-3 unrelated populations under alphabetical order -- confirmed visually and via a new hand-verifiable test (`test-admixture.R`) using a synthetic fixture where two similar populations are deliberately named to sort apart alphabetically (`A_pop`/`C_pop` similar, `B_pop` different) and are recovered as adjacent regardless. Verified end to end against the real reference pipeline run: exactly the 32 population-organized Q-matrix/membership figures (every K across all three backends plus DAPC) changed, nothing else. No public API changes.

- Added spatial autocorrelation analysis (Smouse and Peakall 1999), a distance-class correlogram complementing the single overall Mantel r the `ibd` module already computes, found by the same standard-toolkit audit. New `spatial_autocorrelation` module (on by default via `analyses.spatial_autocorrelation`, needs geographic coordinates like `ibd`) bins sample pairs into equal-width geographic-distance classes and computes an autocorrelation coefficient r per class from a squared individual genetic-distance matrix, with a permutation-based null envelope and two-sided p-value per class (`analyses.spatial_autocorrelation_bins`, default 10; `analyses.spatial_autocorrelation_permutations`, default 999, matching the existing Mantel permutation convention). New `50_spatial_autocorrelation.tsv` and figure (a correlogram: r vs. distance class, with the permutation envelope as a shaded band).

  Verified two ways before shipping, not just formula-derived by hand: (1) the per-locus genetic-distance term reduces algebraically for biallelic markers to the squared difference in genotype dosage -- confirmed, not just derived, by sourcing the reference implementation's own R source directly (`PopGenReport::gd.smouse()`, Adamack and Gruber) and comparing outputs on a synthetic fixture, matched to floating-point precision; (2) the r-per-distance-class statistic (classical Gower 1966 double-centering of the squared-distance matrix) matched `PopGenReport::spautocor()`'s own source exactly (max absolute difference ~1e-16, machine precision) on the same fixture. `PopGenReport` itself is not installable as a dependency in every environment (its own package dependencies -- raster/terra/gdistance -- are unrelated to this specific functionality and failed to build even in the development environment used here), so only the small, self-contained, already-verified pieces are reimplemented, sourced directly for verification rather than requiring the whole package. One real, minor quirk found and deliberately not replicated: the reference's own permutation shuffles the lower and upper triangles of the genetic-distance matrix independently, which can produce an asymmetric matrix; this package instead permutes individual labels jointly (the standard Mantel-style permutation `vegan::mantel()` already uses elsewhere in this codebase), which is the more conventional, symmetry-preserving approach.

  Real quickstart result, and an important, honest caveat investigated before writing it up: several of the shortest distance classes have zero pairs, and most classes show negative or non-significant r. This traces directly to the quickstart dataset's geography: because its 8 populations use real, documented *population-level representative coordinates* (not per-individual GPS -- true individual locations are never published for de-identified 1000 Genomes samples), 2,720 of 12,720 sample pairs (21%) are at exactly zero geographic distance (same population, or the populations sharing one representative point), and the smallest *nonzero* distance is 3,503 km -- a large gap with no pairs at all in the two shortest bins under the reference method's standard open-at-zero binning convention (confirmed directly from the geographic-distance matrix, not assumed). This means the correlogram mostly resolves population-site-to-site differences rather than the fine-grained, continuous individual-level spatial autocorrelation the method was originally designed to detect, and the real quickstart values should be read with that resolution limit in mind, not as evidence about within-population spatial genetic structure. New `spatial_autocorrelation_module_spec()`, `references = "Smouse and Peakall 1999"`. Refreshed the public API baseline (637 -> 638 entries). No public API changes beyond the new module-spec export.

- Added Jost's (2008) D, an alternative population-differentiation measure to FST, found by the same standard-toolkit audit that previously surfaced Nm. FST is mathematically constrained by within-population heterozygosity -- a highly polymorphic marker set can never show a high FST even under strong true differentiation -- and Jost's D ("GST and its relatives do not measure differentiation", Molecular Ecology) was specifically designed to avoid that constraint, so it directly complements rather than duplicates FST's existing role. New `global_jost_d` column on `17_global_FST.tsv`, `jost_d`/`jost_d_n_snps` columns on `18_pairwise_FST.tsv`, and a new `19b_pairwise_jost_d_matrix.tsv`, matching the existing FST table conventions; no new figure. Reuses `compute_diversity()`'s already-computed per-population, per-locus allele frequencies (`context$diversity_full$locus`) rather than a new per-locus computation -- `fst_module_spec()` now declares `requires = "diversity"` to guarantee that data exists before the module runs (previously undeclared, relying only on incidental registry-list ordering, which the scheduler's dependency-wave logic does not actually guarantee once a module needs another module's context output).

  Uses the Nei and Chesser (1983) bias-corrected Hs/Ht estimators, matching the standard reference R implementation (`mmod::D_Jost()`, Winter 2012) exactly. Verified two ways before shipping, not just formula-derived by hand: (1) a small, fully hand-computable two-population example (p = 0.2 and 0.8, n = 10 each) pinned to 10 decimal places; (2) `mmod` (not a dependency of this package, installed only for this verification) run on a synthetic four-population fixture with unequal, non-round sample sizes (15/22/9/18) for both the global and a pairwise (two-population) case -- this package's own implementation matched `mmod::D_Jost()`'s output to floating-point precision (max absolute difference ~2e-16) in every case tested. The pairwise-D result is pinned in `test-jost-d.R` as a literal derived from that real cross-check, not re-installing `mmod` at test time.

  Real quickstart result: global Jost's D = 0.0387 (versus global FST = 0.0915 -- Jost's D is numerically smaller than FST here, an expected, well-documented property of the two measures, not a discrepancy). Pairwise D correlates strongly with pairwise FST (r = 0.998) but is not a strict re-ranking of it: FST's closest pair is ITU-STU (FST = 0.00515) with LWK-YRI a close second (FST = 0.00523), while Jost's D reverses that order (LWK-YRI closest at D = 0.00196, ITU-STU second at D = 0.00211) -- both pairs are near-ties on both measures, so this is presented honestly as the two statistics agreeing overall while not being interchangeable in fine detail, not as a contradiction. - Added two more genuine analysis gaps found by the same standard-toolkit audit: Kimura and Crow's (1964) effective number of alleles (Ae) alongside the existing diversity metrics, and a folded site frequency spectrum with the mode-shift bottleneck-detection test (Luikart and Cornuet 1998).

  **Effective number of alleles (Ae).** `compute_diversity()` (`R/diversity.R`) now computes `Ae = 1 / (1 - He_unbiased)` per locus (a new `effective_alleles` column on `10_population_locus_diversity.tsv`) and its per-population mean (a new `mean_effective_alleles` column on `09_population_diversity.tsv`, averaging the per-locus values rather than transforming the mean He, matching GenAlEx's convention -- these are not interchangeable by Jensen's inequality). No new table, no new figure -- a small, low-risk addition alongside the existing observed/expected heterozygosity and allelic richness columns. `He_unbiased`'s small-sample bias correction can legitimately push it to or past 1 for very small per-population samples, in which case `Ae = Inf` is reported rather than a fabricated finite number (matching the Nm/Ne(LD) convention); this is a real, expected property of the *unbiased* He estimator, not a bug -- caught while writing the validator: an initial `effective_alleles <= 2` bound (mirroring allelic richness's genuine combinatorial ceiling) is actually **not** a valid constraint for Ae, since it is a bias-corrected continuous estimator whose point estimate can exceed the biallelic true-parameter bound under small-sample sampling noise (the same class of behavior already accepted for W&C84 FST going slightly negative elsewhere in this codebase); the validator checks `Ae >= 1` instead, the one bound that always holds. Verified with `test-allelic-richness.R`, reusing its existing hand-computed fixture: exact per-locus Ae values pinned by hand, a dedicated single-heterozygous-call fixture confirming the `Ae = Inf` edge case, and the corrected validator bound. Real quickstart result: `mean_effective_alleles` ranges 1.44-1.51 across the 8 populations. No public API changes.

  **Site frequency spectrum and mode-shift bottleneck screen.** New `bottleneck` module (`R/bottleneck.R`, on by default via `analyses.bottleneck`, needs population metadata like `diversity`/`ne_ld` but works with a single population -- unlike `population_tree`/`population_assignment`, this is a within-population test, not a between-population comparison) bins each population's segregating loci by folded minor allele frequency (`analyses.bottleneck_n_bins`, default 10 classes spanning 0-0.5) into a new `48_site_frequency_spectrum.tsv` and figure, then applies the mode-shift test (Luikart and Cornuet 1998): under mutation-drift equilibrium the lowest frequency class is expected to hold the most segregating loci (an "L-shaped" spectrum); a mode shifted to a higher class is a possible recent-bottleneck signature, reported per population on a new `49_bottleneck_mode_shift.tsv`. Deliberately implements the qualitative screening version of the test (as the BOTTLENECK software also offers), not a p-value -- explicitly documented as a signal worth investigating further, not a confirmed bottleneck. Unlike the classic heterozygosity-excess bottleneck test, mode-shift makes no assumption about the locus mutation model (infinite-alleles vs. stepwise), so it is a clean fit for biallelic SNP data, unlike the heterozygosity-excess test. Reuses `compute_diversity()`'s already-computed per-locus `maf`/`polymorphic` columns via `context$diversity_full` (`requires = "diversity"`) -- no new per-locus computation. New `bottleneck_module_spec()`, `references = "Luikart and Cornuet 1998"`. Verified with `test-bottleneck.R`: hand-computed binning and mode-detection for both the expected (mode at the lowest class) and mode-shifted cases, the monomorphic-locus exclusion (matching standard SFS convention -- only segregating sites contribute), the right-closed class-boundary behavior, the empty-population edge case, the figure, and the validator.

  Real quickstart result, and an important, honest caveat: with this package's default `qc.maf = 0.05` filter (applied globally, pooled across all populations, before this or any other module runs), **all 8 populations** show `mode_shifted = TRUE` in the shipped result. Investigated before writing this up rather than reporting it uncritically: re-running the same analysis against the same GDS with the MAF filter disabled (`qc.maf = 0`) shows only 3 of 8 populations (ITU, STU, YRI) are genuinely mode-shifted; the other 5 (CHB, GBR, LWK, PEL, PUR) correctly show the expected unshifted, lowest-class mode once the filter is removed. This confirms the default MAF filter -- which systematically removes population-rare variants before this test ever sees the data -- is a real, general source of artifactual mode-shift signals for the mode-shift test (and, more broadly, for any SFS-based method) on any MAF-filtered marker set, not a demographic finding specific to this dataset. This is the same general class of caveat already documented for Tajima's D's own MAF-filtering bias; a user investigating a genuinely suspected bottleneck should rerun with a low or zero `qc.maf` to get an unbiased SFS. Documented honestly in the wiki/vignette alongside the shipped (default-config) result rather than presenting all-populations-bottlenecked as a real finding.

- Added two genuine analysis gaps found by auditing the package against a standard population-genomics toolkit (the same audit method that previously surfaced kinship, ROH, genome scans, LD decay, Ne(LD), and Nei's distance): Wright's (1931) island-model gene-flow estimate (Nm) alongside FST, and a frequency-based population self-assignment test.

  **Nm (gene flow) from FST.** `run_fst()` (`R/fst.R`) now computes `Nm = (1 - FST) / (4 * FST)` (a new `fst_to_nm()` helper) alongside every FST estimate it already produces: a new `global_nm` column on `17_global_FST.tsv` and a new `nm` column on `18_pairwise_FST.tsv`, no new table files, no new figure (the existing `10_pairwise_FST` heatmap and its underlying FST values are unchanged; Nm is a direct, monotonic transform of FST already shown there). `FST <= 0` (no detectable differentiation, including small-sample W&C84 negative noise) reports `Nm = Inf` -- no evidence of restricted gene flow, not a fabricated finite number, matching this codebase's established convention for `ne_ld()`'s undetectable-drift-signal case. `fst_module_spec()`'s `references` now cites Wright 1931 alongside Weir and Cockerham 1984. Verified with `test-fst-nm.R`: the formula pinned against hand values (FST = 0.05 -> Nm = 4.75), the zero/negative-FST -> Inf branch, NA propagation, and a real end-to-end check that `run_fst()`'s `global_nm`/`nm` match `fst_to_nm()` applied to its own `global`/`long$fst`. Real quickstart result: global FST = 0.0915 -> Nm = 2.48; the closest pairwise population pair by FST is ITU-STU (FST = 0.0052, Nm = 48.3) and the second-closest is LWK-YRI (FST = 0.0052, Nm = 47.6) -- both already known from this package's own Nei's-distance work as the two most genetically similar pairs in this dataset, an independent, cross-method confirmation. No public API changes.

  **Population assignment test.** New `population_assignment` module (`R/population_assignment.R`, on by default via `analyses.population_assignment`, needs population metadata and at least two populations like `population_tree`): a frequency-based self-assignment test (Paetkau et al. 1995, 2004) that scores each sample's leave-one-out genotype log-likelihood (Rannala and Mountain 1997's bias correction -- a sample's own genotype is excluded from its own recorded population's allele-frequency estimate before scoring against it) under every population's allele frequencies (assuming Hardy-Weinberg equilibrium), then assigns it to whichever population maximizes that likelihood. A sample whose assigned population differs from its recorded metadata label is a candidate migrant or a metadata error -- the same "does the data match the metadata" question kinship and sex_check already ask, now applied to population identity. Uses the LD-pruned marker set (like kinship/PCA/IBS), not the full QC-passing set diversity/HWE use: the per-locus likelihoods are multiplied together assuming independence across loci, which linked markers would violate, inflating apparent assignment confidence. A population fixed for the other allele at a locus is corrected to the standard `1/(2n)` minimum-observable-frequency (Paetkau et al. 2004's convention, also GenAlEx's default) rather than a hard zero, which would let one locus veto that population outright with a log-likelihood of `-Inf`; a locus with zero calls in a candidate population is excluded from that population's score entirely, the same locus-exclusion convention `population_tree.R` already uses for Nei's distance.

  New `47_population_assignment.tsv` (per-sample `recorded_population`/`assigned_population`/`mismatch`/`log_likelihood`/`likelihood_ratio`/`posterior_probability`/`n_loci_used`) and a `47_population_assignment` confusion-matrix heatmap figure (recorded population by row, assigned population by column, matching the existing pairwise-FST heatmap's visual style). New `population_assignment_module_spec()`, `references = c("Paetkau et al. 1995", "Paetkau et al. 2004", "Rannala and Mountain 1997")`. Verified with `test-population-assignment.R`: an exact hand-computed fixture (two populations, one locus, one deliberately mislabeled sample per population) pinning the leave-one-out log-likelihood values and the resulting mismatch flags exactly; the zero-calls-locus exclusion; the fewer-than-two-populations empty result; a larger synthetic 3-population fixture with known, well-separated allele frequencies recovering >90% correct self-assignment; the figure; the validator; and registry wiring.

  Real quickstart result: 106/160 samples (66.25%) correctly self-assign; the 54 mismatches are heavily concentrated in exactly the two most genetically similar population pairs identified above by FST/Nm -- 19 of 54 are ITU/STU cross-assignments and 12 of 54 are LWK/YRI cross-assignments (31/54, 57%), with a 357-SNP marker panel genuinely unable to cleanly separate these closely related population pairs, not a defect in the method. This is a real, textbook population-genetics result and an independent cross-validation of the same closely-related-population-pairs finding from the FST/Nm and Nei's-distance work, using an entirely different statistical approach (per-sample genotype likelihood rather than aggregate allele-frequency distance).

- Parallelized `render_report()`'s HTML and PDF rendering when both formats are requested (the default): previously `vapply()` rendered them strictly sequentially, so a full report always paid the HTML render cost followed by the (typically slower, LaTeX-compiled) PDF render cost in series. On non-Windows platforms, both formats now render concurrently via `parallel::mclapply()` (fork-based, already a hard dependency via `parallel`) -- roughly halving report wall-clock time for the common case. Windows has no fork support, so `render_report_formats()` (the new small dispatch helper `render_report()` now delegates to) explicitly detects `.Platform$OS.type == "windows"` and always falls back to the original sequential path there; a single requested format also always takes the sequential path (nothing to parallelize).

  This required a real correctness fix to make concurrent rendering safe, not just faster: `render_standard_report_format()` previously let `rmarkdown::render()` default its knit `intermediates_dir` to the same directory as the shared input template (`system.file(...)`, one physical file for both formats) -- fine sequentially, but two renders racing on the same intermediate filenames concurrently would corrupt each other. Fixed by giving each format its own `tempfile()`-backed `intermediates_dir`, cleaned up via `on.exit()`; this fix is unconditionally in effect (both the sequential and parallel paths benefit), not gated on whether parallel rendering actually runs.

  `mclapply()` does not propagate a worker's error as a normal R condition the way sequential `lapply()`/`vapply()` do -- a failure is returned in-place as a `"try-error"`-classed value instead of being thrown. `render_report_formats()` explicitly detects this and re-`stop()`s with the original error message, preserving the exact error-throwing behavior `render_report()`'s callers (including its own tests) already depend on. Verified with a real end-to-end `render_report(..., formats = c("html", "pdf"))` render (both real files produced, correctly named/keyed) plus unit coverage of the new dispatch helper directly: single-format sequential dispatch, multi-format parallel dispatch with correct naming/ordering, and error re-signalling from a failing worker. No public API changes (`render_report_formats()` is internal; `render_report()`'s signature, return shape, and default behavior are unchanged).

- Added a partial Mantel test to the `ibd` module, controlling the existing Mantel test's genetic-vs-geographic distance correlation for population identity -- the standard landscape-genetics follow-up question of whether an isolation-by-distance signal holds once population membership is accounted for, or is purely an artifact of population clustering. Caught before shipping: the binary same/different indicator only fully collapses onto (is perfectly collinear with) geographic distance when there are exactly two populations (a single between-population distance value); with three or more, real, testable residual variance remains even when coordinates are population-level rather than individual GPS -- confirmed with two synthetic multi-population smoke tests before finalizing the shipped code comment. This package's own quickstart dataset (8 populations) is nowhere near the degenerate case.

(partial, controlling for population: r = ..., p = ...)"`), falling back to the plain-Mantel-only subtitle otherwise; no change to the figure's points/curve. `ibd_module_spec()`'s `references` now cites Smouse, Long, and Sokal 1986 alongside Mantel 1967 and Rousset 1997. - Added LD-based contemporary effective population size (Ne), the next gap found by the same standard-toolkit audit that surfaced kinship, ROH, genome scans, LD decay, and allelic richness -- and a natural extension of the LD-decay module added just above, though it needs an unrelated pair-selection strategy (unlinked pairs, not physically close ones).

  New `ne_ld` module (`R/ne_ld.R`, on by default via `analyses.ne_ld`, per population like `diversity`) implements the Waples (2006)/Waples & Do (2008) "LDNe" method: per-population Ne from mean r-squared between *cross-chromosome* SNP pairs (`SNPRelate::snpgdsLDMat(..., slide = -1)`, the already-verified full-pairwise-matrix mode, restricted to pairs on different chromosomes -- the opposite pair selection from `ld_decay`, which specifically wants physically close pairs), bias-corrected for sampling noise, then converted to Ne via `Ne = (1/3 + sqrt(1/9 - 2.76*r2_drift)) / (2*r2_drift)`. The bias correction itself is piecewise in the harmonic-mean sample size S (`E(r2) = 0.0018 + 0.907/S + 4.44/S^2` for S <= 30, `1/S` for S > 30) -- both formulas were independently cross-checked against multiple secondary sources before shipping (not just recalled), not just algebra-consistency-checked against each other. Reuses this package's existing QC MAF filter (default 0.05) to satisfy the bias correction's own documented rare-allele-exclusion assumption, rather than adding a redundant `Pcrit` parameter. r-squared attributable to drift at or below the sampling-noise floor is reported as `Ne = Inf` (no detectable signal, not a fabricated finite number, matching NeEstimator's own convention); an implied-Ne below the formula's valid domain is reported as `NA` with an explicit `below_formula_domain` status, never a bogus complex/negative root.

  New `45_Ne_LD.tsv` (per-population `n_samples`/`n_snps`/`n_chromosomes`/`n_pairs`/`harmonic_mean_n`/`mean_r2`/`mean_r2_drift`/`ne`/`ne_status`) and a `45_Ne_LD` figure (log-scale points by population, omitting non-finite estimates). New `analyses.ne_ld_max_snps` config key (default 2000, a deterministic subsample cap bounding the O(n^2) full pairwise-LD computation for large marker sets -- SNPRelate's own C implementation makes the *quickstart-scale* full matrix trivially fast, verified directly: under 0.2 seconds for the real chr22 marker set). `ne_ld` requires population metadata like `diversity`/`allelic_richness` (added to `metadata_capabilities.R`'s `population_modules`) and is explicitly disabled in `template_config()` alongside the other population-requiring analyses, matching that config's own documented intent.

  Deliberately did **not** implement a jackknife confidence interval in this pass, unlike this package's other estimators with bootstrap/jackknife CIs (FST, diversity): the point-estimate formula and its bias correction were independently verified against multiple sources with high confidence, but a precise reproduction of NeEstimator's own parametric jackknife CI construction could not be independently confirmed from available sources, and shipping a plausible-looking but unverified CI formula was judged a worse outcome than an honestly incomplete v1 -- tracked as a real, documented limitation rather than a silently wrong number.

- Added runs-of-homozygosity (ROH) detection and per-sample FROH, the other genuine gap flagged alongside kinship earlier this session: diversity's `inbreeding_coefficient` is a population-level FIS summary and kinship is pairwise, but neither captures the per-sample, per-genomic-region signal of long homozygous stretches (a standard inbreeding/autozygosity indicator). Uses `bcftools roh` (Narasimhan et al. 2016, HMM-based, the modern standard method) -- `bcftools` is already a **required** `SystemRequirements` dependency (used for VCF sorting/BGZF/indexing before the pipeline can even build a GDS), so this adds **no new dependency at all**. The only CRAN alternative, `detectRUNS`, was checked and rejected: last updated 2019, `NeedsCompilation: yes`, and pulls in 6 dated transitive dependencies (`plyr`/`iterators`/`itertools`/`reshape2`/`Rcpp`/`gridExtra`) for one feature. Verified empirically against real data before committing to the design: `bcftools roh -G30 --estimate-AF -` (self-estimated allele frequencies from the analyzed samples -- this package has no mechanism to attach an external reference-panel AF to an arbitrary VCF, so self-estimation is the only sound default) against the real, already-approved chr22 1000 Genomes region gave real, plausible signal (a 15-sample real multi-population subset: 1-4 runs of 15-160kb per sample within a 1Mb window, FROH 0.02-0.4); confirmed `--AF-dflt` (a naive constant AF) produces obviously-degenerate output (near-100%-of-window "runs" for every sample), ruling it out. Deliberately does **not** apply this package's fixed MAF filter (`maf=0.05`) before ROH calling -- MAF filtering is appropriate for PCA/structure work but is known in the ROH literature (Purcell et al. 2007; McQuillan et al. 2008) to bias run lengths downward by removing informative rare-homozygous tracts; ROH instead reuses only the *missingness* half of the fixed QC contract (`F_MISSING > 0.2`, i.e. `cfg$qc$max_variant_missing`, not a new config key) plus a biallelic-SNP-only restriction. New `R/roh.R`: `run_roh()` derives the exact analyzed sample/site subset via one `bcftools view` call, computes the **analyzed genomic footprint** (not the whole genome -- this package accepts arbitrary VCF inputs, so a single-region VCF and a whole-genome VCF give very different FROH for the same biology) from that same site set, and calls `bcftools roh`, producing a full per-run table and a per-sample summary where a sample with zero detected runs still appears with `n_runs=0`/`froh=0` (real information, not silently omitted). New module `roh_module_spec()` writes `37_ROH_runs.tsv`, `38_ROH_sample_summary.tsv`, and two new figures: `23_ROH_length_distribution` (log-scale histogram, skipped only when zero runs exist anywhere) and `24_ROH_FROH_by_sample` (always drawn, coloured by population when available). New `analyses.roh` config key (default `TRUE`, like `ibs`/`kinship` -- bcftools being mandatory rather than optional is exactly why) and `analyses.roh_gt_error_phred` (default 30, bcftools's own documented "safe value... to account for GT errors"). Deliberately does not impose any short/medium/long ROH-length classification convention (species/study-specific, not a property of the estimator itself, unlike KING's kinship thresholds) and does not expose genetic-map/HMM-transition-probability tuning (no supply mechanism for species-specific genetic maps in this general-purpose tool). Report gained a NULL-safe "Runs of homozygosity" section (highest-FROH samples, capped at 20, pointing to the complete on-disk table), matching the "Close relatives"/"Private alleles" precedent. Verified with a new `test-roh.R`, including a purpose-built synthetic VCF fixture with real, verifiable ground truth (one sample homozygous throughout -> one run spanning the full analyzed span; one heterozygous throughout -> zero runs), plus real-data smoke checks against the cached chr22 region and the tiny bundled CI fixture (structural-only, matching the established HWE/kinship precedent for that undersized fixture). No public API changes: only `roh_module_spec()` is exported, matching every other `*_module_spec()`.
- Added pairwise sample kinship/relatedness estimation, a genuine gap distinct from the existing IBS analysis: IBS answers "how similar are these samples overall," kinship answers "are these two individuals related, and how closely" -- the standard upstream check for cryptic relatives, which silently biases FST, diversity, and structure analyses computed downstream. Uses `SNPRelate::snpgdsIBDKING()` (KING-robust, Manichaikul et al. 2010, already an SNPRelate dependency -- no new package). `type = "KING-robust"` is hardcoded rather than exposed as a config toggle: `"KING-homo"` assumes a single homogeneous population and would silently give biased results whenever real population structure exists, which this package explicitly supports. Verified empirically before committing to the design: the tiny 9-SNP CI validation fixture gave nonsensical kinship values (outside the theoretical bounds, including identical values for a same-population pair and an arbitrary pair), confirming KING genuinely needs realistic marker density; the real, already-approved chr22 1000 Genomes region (2,504 samples x 21,418 SNPs) gave real signal (the two highest-kinship pairs ~0.48, consistent with 1000 Genomes Phase 3's known duplicate/MZ-twin pairs) in 6.5 seconds. Also discovered empirically, and important for interpretation: KING-robust's kinship estimator is bounded above at 0.5 (self/duplicate) but is **not** bounded below at -0.5 for arbitrarily divergent pairs -- real chr22 data restricted to the pipeline's own LD-pruned SNP set showed off-diagonal kinship as low as -8 for pairs spanning highly differentiated continental populations, so the new validator only enforces the upper bound. New `R/kinship.R`: `run_kinship()` (mirrors `run_ibs()`'s exact filtering defaults) returns the kinship matrix, IBS0 matrix, and a long-form pairs table joined to each member's population, classified into `relationship_degree` (`"duplicate/MZ twin"`, `"1st-degree"`, `"2nd-degree"`, `"3rd-degree"`, `"unrelated"`) using the standard KING thresholds (Manichaikul et al. 2010, not invented). `plot_kinship()` draws `21_kinship_heatmap` (gated at <=300 samples, matching `plot_ibs()`'s existing gate; clusters on a kinship-derived pseudo-distance via the already-generic `hclust_dendrogram_segments()` helper, but displays the real kinship coefficient as fill) and `22_kinship_IBS0_vs_kinship` (the standard KING diagnostic scatter, coloured by relationship degree). New `analyses.kinship` config key (default `TRUE`, like `ibs` -- needs only genotypes, no population/geographic metadata required).
