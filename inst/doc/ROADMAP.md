## 1.0: stable scientific release

Release 1.0 requires stable CLI, YAML, R API, module and output contracts; validated core modules and canonical real-data results; a complete report engine; validated container and Apptainer artifacts; complete documentation and citation metadata; and reproducible release artifacts with checksums, SBOM, provenance, and persistent archive identifiers.

As of the released v0.10.0 state (2026-08-01), every one of those technical criteria is met: the Phase 10 public API/CLI/YAML contracts are stable and CI-enforced; canonical real-data validation, external-tool concordance, and cross-backend ancestry evidence are approved; the Phase 9 publication report engine is complete; container and Apptainer distributions are validated; documentation and citation metadata are complete; and release artifacts (checksums, SBOMs, provenance, DOI) are real and published. What remains before 1.0 is not a technical gate but an explicit decision: 1.0 is a semver commitment (the public API is now stable; future breaking changes require a major version bump), not something CI can prove on its own. Tracked in #4.

## Beyond 1.0

Potential post-1.0 work includes selection scans, genomic landscapes, spatial resistance models, GWAS interoperability, community plugins, interactive exploration, optional Docker Hub publication, and cloud/workflow-platform execution.

- **Temporal effective population size, if a sample-collection-date metadata column is present.** Raised 2026-08-16, deliberately parked rather than built: the classic variance-in-allele-frequency-change method (Nei and Tajima 1981; Pollak 1983; Jorde and Ryman 2007) is a real, distinct complement to the already-implemented LD-based `ne_ld` module -- same target quantity, entirely different estimator, and NeEstimator (the standard reference tool) implements both side by side. The real blocker isn't the statistics, it's that dates alone don't give the method what it needs: samples must be binned into discrete temporal cohorts, and drift accumulates per *generation*, not per calendar year, so a generations-elapsed value (user-supplied or a configured generation-time) is unavoidable. Also only meaningful for datasets with genuinely distinct collection times, not a date column that's constant or effectively continuous. A simpler, lower-effort alternative if this is revisited: temporal FST/differentiation between collection-date cohorts, reusing the existing FST machinery directly with no generation-time parameter needed.

- **Genotype-environment association (GEA), if explicit environmental-covariate metadata columns are present.** Raised 2026-08-17 by a third standard-toolkit gap audit, deliberately parked rather than built: both `LEA::lfmm2()` (LEA is already a `Suggests` dependency, used for `snmf`) and `vegan::rda()`/partial RDA (vegan is already an `Imports` dependency, used for `mantel`/`mantel.partial` in the `ibd` module) are real, currently-unused capabilities of dependencies this package already carries -- a zero-new-dependency win in the same shape that found the `clonality` module via poppr. The real blocker is scope, not engineering: this package's metadata schema currently carries only `latitude`/`longitude` (geographic coordinates), and using those as a stand-in "environment" for `lfmm2`'s `env` argument or RDA's constraining matrix would not test genotype-*environment* association in the sense that gives GEA its scientific value (candidate loci associated with climate/habitat/soil gradients) -- it would instead re-test spatial genetic structure, substantially overlapping the existing Mantel/partial-Mantel IBD test and PCA output, without the genuinely new signal GEA methods are prized for. A defensible, non-redundant implementation needs new, explicit, user-supplied environmental-covariate metadata columns, the same kind of scope decision as the temporal-Ne idea above. Checked and ruled out in the same audit round: `rehh` (EHH-based selective sweep detection) needs phased haplotypes, which this pipeline does not produce -- a hard blocker, not a scope choice; `admixtools2` (f2/f3/f4-statistics, qpAdm) is real and methodologically distinct from the existing ADMIXTURE/fastStructure/sNMF cluster-assignment backends, but is GitHub-only (same rejection criterion already applied to `radiator`); `EEMS` remains a standalone external program with no CRAN R interface.
